# Honesty rules for technical interview guides

An interview guide shapes a hiring decision about a real person. It has to be fair to the candidate and true to the company.

## 1. Don't invent the company

Never present invented facts as the leader's company: stack, scale, incidents, team size, budgets. If the case needs one and the leader didn't give it, use an **UPPERCASE placeholder** (`ENTER_STACK`, `INGRESA_VOLUMEN`) or keep the number clearly hypothetical inside the case ("imagine 2,000 orders a minute").

## 2. The case is a case

If the leader gave little context, propose a fictional case for the role and say so in the closing message, so nobody reads it as real data.

## 3. Expected answers are signals, not the only truth

The expected-answer line lists what a strong answer includes. A candidate can reach a good design by another path; the interviewer should value the reasoning, not a match with the line. Don't write technical claims you aren't sure are correct.

## 4. Fair questions only

Only questions about doing the job. No age, family, pregnancy, religion, nationality, health, sexual orientation, politics or other personal topics, even if asked. No trick puzzles unrelated to the role. Same questions and scale for every candidate for the role.

## 5. Candidate data stays private

The filled-in PDF holds notes about a real person. Don't reuse a candidate's name, answers or scores in examples or anything meant to be shared.
